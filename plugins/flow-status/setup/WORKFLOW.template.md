# Personal development flow (local, not committed)

Default preference, not mandatory: follow the user's chosen alternative, including full GSD, when explicitly requested. Canonical personal workflow for Claude and Codex. Claude and Codex load this shared file; keep the workflow here only. Repository policies and explicit user instructions take precedence.

Conversation before workflow:

- Start with a normal conversation about the task. Answer questions, explore options and tradeoffs, and clarify intent using the existing context. Read-only investigation is allowed when useful; do not turn the discussion into a formal intake or checklist.
- A task idea, ticket mention, or exploratory question does not by itself start the feature workflow. During discussion, do not create PLAN.md, DISCOVERY.md, FLOW.json or GSD records, create a feature worktree, or dispatch planning/review agents.
- Start formal planning when the user explicitly asks for a plan or a named workflow. Otherwise, when the context sufficiently establishes the problem, desired outcome, scope and material constraints, briefly summarize your understanding and ask whether the user wants to formalize it into a plan. Wait for agreement before starting; enough context alone is not approval. Do not repeatedly offer planning while the user is still exploring.
- Reuse decisions and context already discussed once planning starts; do not restart discovery or ask answered questions. Approval to prepare a plan is separate from approval to implement it.
- Small, clear, directly requested edits may be completed without the feature workflow. Respect an explicitly chosen alternative and resume an already approved workflow without asking to start it again.

## Local flow identity

A flow needs no Linear issue or external ticket. Choose a stable local flow ID such as `cache-cleanup`. Schema 1 keeps the historical `ticket` key for that required ID; normally use the same ID as the draft directory name. Omit `linear_id` or set it to `null` when unlinked, and use `prs: []` until a PR is attached. Never infer a Linear association from the local ID, folder, title or branch. Existing linked records keep their explicit associations. Render the plan/discovery heading markers with the local flow ID and title when creating a real draft.

The workflow below applies after the user chooses formal planning:

- Discover named WNZ skills and required dependencies through the host; stop affected work if missing. Skills own role/model policies and workflow algorithms; do not duplicate them here.
- Give reviewers requirements and FLOW.json `simplicity` decisions as unbiased evidence. Prefer correct removal or reuse; unresolved requirement conflicts need the user's decision.
- Each flow's private dashboard projection lives in `{{PRIMARY_REPO}}/.planning/drafts/<flow-id>/FLOW.json` (untracked; schema: `{{FLOW_PLUGIN_ROOT}}/src/flowCore.ts`). Keep only `PLAN.md`, `DISCOVERY.md` and `FLOW.json` there (extra files only when condensing would lose decisions; list them in `DISCOVERY.md`). The coordinator writes supported review summaries, approvals, simplicity removals, task status and resume notes into FLOW.json; use existing evidence strings for authoritative artifact pointers. After each write set `updated_at`, `step`, the step's `steps[n]` evidence, and run `{{VALIDATE_COMMAND}}`.
- FLOW.json carries static dashboard timing and titles; never invent either. When `step` moves to a step, write `steps[n] = {state: "active", evidence, started_at}`. When the step ends, set its final state and `completed_at`. Moving back to an earlier step: mark a step done only if it really finished; remove an unfinished step's record. Re-entering a step keeps its first `started_at` and removes `completed_at`. Write each task as `{status, summary, started_at, completed_at}`, copied from the executor ledger task's `title`, `started_at` and `completed_at`. Omit a field the ledger marks `none` or unavailable. Map ledger status to `pending` (not dispatched), `in_progress` (active or reopened) or `done` (completion recorded). If a title exceeds 200 characters, keep the first 199 and append `…`. Reopening a task keeps `started_at` and removes `completed_at`. Times are ISO-8601 with offset and no later than `updated_at`. Elapsed is wall-clock time, including reviews, retries and pauses. Plain status strings and missing times are legacy forms only. Fix every validation error. Only if errors show the validator does not know these fields (a task object rejected as a non-enum value, `active` rejected as an unknown step state, or `started_at`/`completed_at` rejected as unrecognized keys) is the plugin outdated: then write that record in the legacy form and report the outdated plugin.
- `wnz-phase-executor` owns the authoritative execution ledger and detailed role reports. Resolve its runtime references, including `references/coordinator-templates.md` and `references/coordinator-boundary.md`, through the host-discovered skill. Keep that one ledger and its reports in an approved ignored location or external scratch path under executor rules, outside the draft folder; this exception permits required executor evidence, not arbitrary extra files or duplicate transcripts. Never add unsupported gate, dispatch, source-state or role-status fields to schema 1. FLOW.json and GSD summarize supported state and point to canonical evidence; neither can approve an executor gate. On resume recover the canonical ledger and required reports first; missing artifacts block dependent execution even when FLOW.json says done or approved.
- GSD is the shared, tracked record; write through to it only at milestones: step 8 first creates the flow's feature branch from `{{BASE_BRANCH}}` (or switches to it) in its own worktree, never the shared main checkout on `{{BASE_BRANCH}}`, adds it to FLOW.json `branches`, then registers GSD as step 8 specifies, creating the quick folder (decisions + short discovery summary + the verbatim approved plan, in `gsd-quick`'s own file names); gsd-quick does not add the `Registered Work` row, so add it to .planning/STATE.md yourself; set FLOW.json `gsd_quick`. Steps 9 and 11 update the quick folder's state/summary file and that row's status with task, review and PR progress. Step 13 content (the quick SUMMARY, and moving the row to `Quick Tasks Completed` referencing the PR number, not a merge sha) is committed as the last commit on the feature branch after the final review and PR review loop pass and before the merge, so it ships in the PR; step 13 is then marked after the merge. Make every later GSD write in that branch/worktree too and commit them there so they reach `{{BASE_BRANCH}}` with its PR. Never copy FLOW.json itself into GSD, and name draft paths there as plain text, never Markdown links.

1. Carry the conversation into planning and confirm any unresolved scope before implementation.
2. Prepare the plan in a fresh `wnz-implementation-planner` sub-agent, including its template and self-review, without implementation. Defer the independent plan gate to step 4 after the simplicity pass.
3. Run `wnz-plan-simplicity-review` on the whole plan (fresh sub-agent). It may edit the plan and records what it removed and why in FLOW.json `simplicity`.
4. Apply `wnz-phase-executor`'s `references/independent-plan-review.md` gate with a fresh, read-only `wnz-plan-reviewer`. Use `wnz-implementation-planner` for corrections. Follow the gate's cycles, two-round cap and annotation rules; record verdict and evidence for the latest semantic revision in FLOW.json `reviews`.
5. If review changes add anything material, re-run the simplicity review on those changes only.
6. Offer Plannotator annotation when the plan is ready; open it on request and incorporate the feedback (feedback starts a new review cycle).
7. Wait for user approval of the plan and its decision points before implementation; record it in `approvals.plan`.
8. Register the approved plan using the installed `gsd-quick` initialization and artifact conventions for tracking. Read that client's workflow and stop before planner/executor dispatch; a full quick invocation also executes work. Preserve approved tasks and decisions without replanning. Record the quick path in `gsd_quick`.
9. Execute with `wnz-phase-executor`; it owns `wnz-task-implementer` dispatch, verification, independent `wnz-code-reviewer` task reviews and fix loops. Do not add duplicate gates. Keep detailed execution and review evidence in its canonical ledger/reports; project supported summaries and evidence pointers into FLOW.json.
10. Content (banks, reference answers, fixtures): model draft, independent content review, user approval, then freeze; record the approval in `approvals.content`.
11. Prepare the PR with release notes before the executor's final aggregate review. Use one fresh `wnz-code-reviewer` pass over the full branch/PR scope to satisfy both the executor's final aggregate gate and the initial PR review. Follow its fix/re-review loop for findings or subsequent changes; do not redispatch an already passed review of unchanged scope. Before merge, require no requirement gaps or unresolved High/Medium findings and green CI on the final reviewed head, including later GSD commits. Record `prs`, then merge using `{{MERGE_METHOD}}`. After the merge record the merge sha in FLOW.json only. Keep the flow active while required verification, explicitly authorized live runs or GSD result updates remain.
12. Paid or live runs only with explicit user approval.
13. Update GSD context, summary and state with execution results and verification evidence. Mark FLOW.json `status: done` and `step: 13` only after the merge and all required work are verified complete. If required runs happen after merge, record pending work honestly in the premerge summary; publish later GSD results through the repository-approved follow-up branch/PR process, not direct writes to a shared integration checkout.

## Linked worktrees and clients

Resolve the primary worktree from the first `worktree` entry of `git worktree list --porcelain`. Private drafts stay there; tracked implementation and GSD milestones belong to the feature worktree. Before starting a new agent session in a linked worktree, install the same private Claude import and Codex loader there, pointing to the primary worktree's shared workflow. Preserve existing client settings, permissions and trust. Do not silently mark projects trusted.

## Shared dashboard

Use the single `herdr.flow-status` plugin from `{{FLOW_PLUGIN_ROOT}}`. It reads `.planning/drafts/<flow-id>/FLOW.json` in the primary worktree and uses the pane's current repository/branch. It is read-only. Open only on request, after resolving and verifying the destination pane from live Herdr state. Never reuse a stale pane ID. Use offline mode for a smoke check. Unassociated flows show `Linear: not linked`; with no attached PRs, live opening and refresh make no provider calls. Missing credentials for linked sources and GitHub checks remain unavailable/none, never success. Optional live Linear reads use `LINEAR_API_KEY` from the Herdr server environment; credentials belong in an approved external mode-600 environment file, never in this workflow, Git or plugin arguments.
