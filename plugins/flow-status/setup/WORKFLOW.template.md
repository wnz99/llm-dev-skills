# Personal feature workflow

Default preference, not mandatory: follow the user's chosen alternative, including full GSD, when explicitly requested. Canonical personal workflow for Claude and Codex. Claude and Codex load this shared file; keep the workflow here only. Repository policies and explicit user instructions take precedence.

Conversation before workflow:

- Start with a normal conversation about the task. Answer questions, explore options and tradeoffs, and clarify intent using the existing context. Read-only investigation is allowed when useful; do not turn the discussion into a formal intake or checklist.
- A task idea, ticket mention, or exploratory question does not by itself start the feature workflow. During discussion, do not create PLAN.md, DISCOVERY.md, FLOW.json or GSD records, create a feature worktree, or dispatch planning/review agents.
- Start formal planning when the user explicitly asks for a plan or a named workflow. Otherwise, when the context sufficiently establishes the problem, desired outcome, scope and material constraints, briefly summarize your understanding and ask whether the user wants to formalize it into a plan. Wait for agreement before starting; enough context alone is not approval. Do not repeatedly offer planning while the user is still exploring.
- Reuse decisions and context already discussed once planning starts; do not restart discovery or ask answered questions. Approval to prepare a plan is separate from approval to implement it.
- Small, clear, directly requested edits may be completed without the feature workflow. Respect an explicitly chosen alternative and resume an already approved workflow without asking to start it again.

## Flow storage cleanup

The flow coordinator owns cleanup of the flow's temporary resources, including artifacts outside the repository. External execution roots such as `~/.local/state/<project>/flows/<flow-id>/` are not permanent storage for every test run.

- At setup, record the exact artifact roots and owned runtime resources in the existing discovery record or execution ledger. Distinguish disposable outputs from authoritative evidence and resources shared with other flows. Do not add dashboard schema fields or create a second ledger.
- After final verification and before marking a flow done, stop its owned processes and remove disposable build outputs, coverage reports, dependency copies, test databases, APKs, duplicate captures, logs and runtime fixtures. Remove flow-owned emulator snapshots or devices only after confirming that they are stopped and no other flow needs them. Preserve uncommitted source work, user data and shared resources.
- Retain the compact canonical plan, ledger, review and verification reports, decisions, PR references and final summary needed to explain the result or resume follow-up work. Preserve unique evidence still required by those records. Before removing bulky evidence, retain its essential findings, commands, results and limitations in the canonical report; update references to identify removed artifacts honestly. Never imply that a deleted artifact remains available or turn a failed run into a successful one.
- At flow start or resume, inspect the sizes of the project's known external flow roots for stale data. Match each candidate to its authoritative flow state and check ownership, outstanding work and live processes. Age or an old folder name alone does not prove that data is disposable. Do not prune active, paused, blocked or unidentified flows; confirm cancellation before treating abandoned work as finished. For completed flows, apply the same cleanup rules to leftover disposable artifacts. Obtain scoped deletion authorization if existing user instructions do not already cover that cleanup.
- Use exact validated paths and the host's coordination rules before deletion. Do not recursively sweep unrelated application containers or request broader macOS permissions for housekeeping. Verify the removals, measure available disk space before and after, and record the removed paths, retained evidence, reclaimed space and any deferred cleanup in the existing final summary. Report cleanup failures explicitly rather than claiming completion.

## PR review loop

This user flow owns the PR loop and its dashboard projection. The coordinator uses the executor's existing dispatch, fix and verification machinery; `wnz-code-reviewer` performs one assigned review pass at a time. Do not start a nested skill-owned loop or add a second final-review gate. One fresh full-branch/PR review satisfies both the executor's final aggregate review and the initial PR review.

1. Start phase 11 before preparing the PR and record its real `started_at`. Before each review dispatch, put a concise first line in FLOW.json `next`, such as `PR review R1: reviewing the full branch`. Dispatch a fresh read-only `wnz-code-reviewer` over the original branch merge base through the current head, including review fixes and relevant consumers. Keep the authoritative review report and reviewed head in the executor ledger; point to them in phase 11's evidence.
2. After each returned pass, append its actual result to `reviews` with `kind: "pr"`, cycle, round, verdict, reviewer model and findings. A shared aggregate/PR pass gets one entry, not duplicate `final` and `pr` entries. Use `CLEAN` for a complete pass with no findings and `FINDINGS` for a complete pass with findings. Schema 1 accepts High, Medium and Low; project a Nit as Low with its original Nit label in the summary, keeping the full report authoritative. An incomplete or unavailable review blocks progress; report it in `next` and evidence without fabricating a completed pass. Preserve existing review history and advance round numbers within the current PR cycle.
3. For unresolved High/Medium findings or requirement gaps, set `next` to `PR review R1: fixing findings` with the actual round and remaining counts, then dispatch authorized fixes through the executor. Verify, commit and push the fixes to the same PR. Update `next` for verification and the next review, then repeat with a fresh reviewer over the full scope. A pushed fix, passing tests, or the author's claim does not close the loop. The two-round plan-review cap does not limit this code-review loop; stop only for convergence, a real blocker, or explicit user direction.
4. The merge gate requires a complete independent code review, no requirement gaps or unresolved High/Medium findings, and green required CI on the current head. Record any accepted Low/Nit residuals. Set `next` to `PR review R2: passed; checking CI` or the actual next action. Reuse a passed review of unchanged scope and state. If a later delta contains only GSD tracking or flow documentation and reviewed executable code, configuration and tests remain unchanged, dispatch a fresh isolated native reviewer through shared routing to validate changed documentation, references and status consistency without another independent code-review cycle. Record the prior reviewed commit, current head, inspected delta and code-equivalence evidence, and reused review/test receipts; do not claim the new head itself was reviewed. Functional code, configuration or test changes require affected fresh verification and review. Material behavior, security or authorization changes do not qualify merely because they appear in Markdown; retain material semantic plan-review gates, initial code review and required CI/merge checks. Keep phase 11 active until the merge finishes; only then record its `completed_at`. FLOW.json reports these facts and never substitutes for the executor's canonical evidence.
