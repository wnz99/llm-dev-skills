# Personal feature workflow

Default preference, not mandatory: follow the user's chosen alternative, including full GSD, when explicitly requested. Canonical personal workflow for Claude and Codex. Claude and Codex load this shared file; keep the workflow here only. Repository policies and explicit user instructions take precedence.

Conversation before workflow:

- Start with a normal conversation about the task. Answer questions, explore options and tradeoffs, and clarify intent using the existing context. Read-only investigation is allowed when useful; do not turn the discussion into a formal intake or checklist.
- A task idea, ticket mention, or exploratory question does not by itself start the feature workflow. During discussion, do not create PLAN.md, DISCOVERY.md, FLOW.json or GSD records, create a feature worktree, or dispatch planning/review agents.
- Start formal planning when the user explicitly asks for a plan or a named workflow. Otherwise, when the context sufficiently establishes the problem, desired outcome, scope and material constraints, briefly summarize your understanding and ask whether the user wants to formalize it into a plan. Wait for agreement before starting; enough context alone is not approval. Do not repeatedly offer planning while the user is still exploring.
- Reuse decisions and context already discussed once planning starts; do not restart discovery or ask answered questions. Approval to prepare a plan is separate from approval to implement it.
- Small, clear, directly requested edits may be completed without the feature workflow. Respect an explicitly chosen alternative and resume an already approved workflow without asking to start it again.

## Local flow identity

A flow needs no Linear issue or external ticket. Choose a stable local flow ID such as `cache-cleanup`. Schema 1 keeps the historical `ticket` key for that required ID; normally use the same ID as the draft directory name. Omit `linear_id` or set it to `null` when unlinked, and use `prs: []` until a PR is attached. Never infer a Linear association from the local ID, folder, title or branch. Existing linked records keep their explicit associations. Render the plan/discovery heading markers with the local flow ID and title when creating a real draft.

The canonical private draft root is the permanent repository main checkout's `.planning/drafts/`, shared by linked worktrees. Find that checkout with `git worktree list`; verify it is a permanent checkout, not bare metadata or a temporary worktree. Do not create a second writable flow in a temporary worktree. On another machine, use its permanent repository checkout and adapt the local absolute dashboard/validator paths below. Shared schema and validator tools remain external user tooling. Preserve existing flow state elsewhere and coordinate migration with its owner before writing; never create a second writable copy. Stop if the permanent checkout is missing or ambiguous.

- Give reviewers requirements and FLOW.json `simplicity` decisions as unbiased evidence. Prefer correct removal or reuse; unresolved requirement conflicts need the user's decision.
- Each flow's private dashboard projection lives in `{{PRIMARY_REPO}}/.planning/drafts/<flow-id>/FLOW.json` (untracked; schema: `{{FLOW_PLUGIN_ROOT}}/src/flowCore.ts`). Keep only `PLAN.md`, `DISCOVERY.md` and `FLOW.json` there (extra files only when condensing would lose decisions; list them in `DISCOVERY.md`). The coordinator writes supported review summaries, approvals, simplicity removals, task status and resume notes into FLOW.json; use existing evidence strings for authoritative artifact pointers. After each write set `updated_at`, `step`, the step's `steps[n]` evidence, and run `{{VALIDATE_COMMAND}}`.
- FLOW.json carries static dashboard timing and titles; never invent either. When `step` moves to a step, write `steps[n] = {state: "active", evidence, started_at}`. When the step ends, set its final state and `completed_at`. Moving back to an earlier step: mark a step done only if it really finished; remove an unfinished step's record. Re-entering a step keeps its first `started_at` and removes `completed_at`. Write each task as `{status, summary, started_at, completed_at}`, copied from the executor ledger task's `title`, `started_at` and `completed_at`. Omit a field the ledger marks `none` or unavailable. Map ledger status to `pending` (not dispatched), `in_progress` (active or reopened) or `done` (completion recorded). If a title exceeds 200 characters, keep the first 199 and append `…`. Reopening a task keeps `started_at` and removes `completed_at`. Times are ISO-8601 with offset and no later than `updated_at`. Elapsed is wall-clock time, including reviews, retries and pauses. Plain status strings and missing times are legacy forms only. Fix every validation error. Only if errors show the validator does not know these fields (a task object rejected as a non-enum value, `active` rejected as an unknown step state, or `started_at`/`completed_at` rejected as unrecognized keys) is the plugin outdated: then write that record in the legacy form and report the outdated plugin.

Persist the phase's real start before doing its work or waiting for approval, then persist its finish before advancing. Premerge GSD summary preparation belongs to phase 11; phase 13 starts only after merge and any required phase 12 work, for final GSD reconciliation and completion verification. Never mark phases 11 and 13 active together. For a skipped or n/a phase, record that decision and its `completed_at`; do not invent a start. Leave unavailable historical times absent and report the gap; never use the resume time, file modification time or `updated_at` as a substitute.

## PR review loop

This user flow owns the PR loop and its dashboard projection. The coordinator uses the executor's existing dispatch, fix and verification machinery; `wnz-code-reviewer` performs one assigned review pass at a time. Do not start a nested skill-owned loop or add a second final-review gate. One fresh full-branch/PR review satisfies both the executor's final aggregate review and the initial PR review.

1. Start phase 11 before preparing the PR and record its real `started_at`. Before each review dispatch, put a concise first line in FLOW.json `next`, such as `PR review R1: reviewing the full branch`. Dispatch a fresh read-only `wnz-code-reviewer` over the original branch merge base through the current head, including review fixes and relevant consumers. Keep the authoritative review report and reviewed head in the executor ledger; point to them in phase 11's evidence.
2. After each returned pass, append its actual result to `reviews` with `kind: "pr"`, cycle, round, verdict, reviewer model and findings. A shared aggregate/PR pass gets one entry, not duplicate `final` and `pr` entries. Use `CLEAN` for a complete pass with no findings and `FINDINGS` for a complete pass with findings. Schema 1 accepts High, Medium and Low; project a Nit as Low with its original Nit label in the summary, keeping the full report authoritative. An incomplete or unavailable review blocks progress; report it in `next` and evidence without fabricating a completed pass. Preserve existing review history and advance round numbers within the current PR cycle.
3. For unresolved High/Medium findings or requirement gaps, set `next` to `PR review R1: fixing findings` with the actual round and remaining counts, then dispatch authorized fixes through the executor. Verify, commit and push the fixes to the same PR. Update `next` for verification and the next review, then repeat with a fresh reviewer over the full scope. A pushed fix, passing tests, or the author's claim does not close the loop. The two-round plan-review cap does not limit this code-review loop; stop only for convergence, a real blocker, or explicit user direction.
4. The merge gate requires a complete independent code review, no requirement gaps or unresolved High/Medium findings, and green required CI on the current head. Record any accepted Low/Nit residuals. Set `next` to `PR review R2: passed; checking CI` or the actual next action. Reuse a passed review of unchanged scope and state. If a later delta contains only GSD tracking or flow documentation and reviewed executable code, configuration and tests remain unchanged, validate changed documentation, references and status consistency without another independent code-review cycle. Record the prior reviewed commit, current head, inspected delta and code-equivalence evidence, and reused review/test receipts; do not claim the new head itself was reviewed. Functional code, configuration or test changes require affected fresh verification and review. Material behavior, security or authorization changes do not qualify merely because they appear in Markdown; retain material semantic plan-review gates, initial code review and required CI/merge checks. Keep phase 11 active until the merge finishes; only then record its `completed_at`. FLOW.json reports these facts and never substitutes for the executor's canonical evidence.

## Linked worktrees and clients

Resolve the primary worktree with `git worktree list --porcelain`; verify the permanent main checkout rather than assuming the first entry is usable. Stop for missing or ambiguous ownership. Private drafts stay there; tracked implementation and GSD milestones belong to the feature worktree. Before starting a new agent session in a linked worktree, install the same private Claude import and Codex loader there, pointing to the primary worktree's shared workflow. Preserve existing client settings, permissions and trust. Do not silently mark projects trusted.

## Shared dashboard

Use the single `herdr.flow-status` plugin from `{{FLOW_PLUGIN_ROOT}}`. It reads `.planning/drafts/<flow-id>/FLOW.json` in the primary worktree and uses the pane's current repository/branch. It is read-only. Open only on request, after resolving and verifying the destination pane from live Herdr state. Never reuse a stale pane ID. Use offline mode for a smoke check. Unassociated flows show `Linear: not linked`; with no attached PRs, live opening and refresh make no provider calls. Missing credentials for linked sources and GitHub checks remain unavailable/none, never success. Optional live Linear reads use `LINEAR_API_KEY` from the Herdr server environment; credentials belong in an approved external mode-600 environment file, never in this workflow, Git or plugin arguments.
